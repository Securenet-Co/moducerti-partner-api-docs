# 모두의인증 연동 API 문서

> **버전 1.2 · 2026-11-24**
> 연동사 서비스에서 모두의인증으로 회원·업체를 등록하고, 인증 신청을 보내고, 진행 상태를 조회하는 API 규격입니다.
> 같은 버전의 OpenAPI 파일(`openapi.yaml`)과 내용이 같습니다. 버전마다 달라진 점은 맨 아래 8절 변경 이력에 있습니다. 문서 버전(1.x)과 API 주소의 버전(`/partner/v1`)은 따로 매깁니다.
>
> **버전 1.1에서 달라진 것(등록 상태)**: 등록 `status`가 `registered`·`certificate_required`·`on_hold` 세 가지가 되었습니다. 버전 1.0의 `review_required`는 **`certificate_required`로 이름이 바뀌었습니다**(뜻은 같습니다: 사업자등록증 파일이 없어 멈춤). 이름을 바꾼 것이라, 버전 1.0 기준으로 만드신 곳은 `status` 값 비교를 고쳐 주세요. 자세한 내용은 3-4와 8절에 있습니다.

## 1. 개요

연동사에서 모두의인증으로 보내는 것은 **API**로, 모두의인증에서 연동사로 알려 드리는 것은 **웹훅**으로 합니다.

| 순서 | 하는 일 | API (연동사 → 모두의인증) | 웹훅 (모두의인증 → 연동사) | 이 문서 |
| --- | --- | --- | --- | --- |
| 1 | 회원·업체 등록 | 회원·업체 등록(회원·업체 한 쌍에 **한 번**), 등록 확인 | — | 3절 |
| 2 | 인증 신청 | 인증 신청(사진·제품 정보, 등록 때 받은 `memberId`를 실음) — 업체마다 **여러 번** | — | 4절 |
| 3 | 진행 및 완료 | 신청 조회(건별·묶음·하루 1회 재대조용 목록), 발급 문서(인증서 등) 내려받기 | 상태가 바뀌면 알림(주 경로). 알림을 놓쳤을 때 조회로 맞춥니다 | 신청 조회는 5절. 발급 문서 내려받기·웹훅은 준비 중(6절) |
| 4 | 정산 | 정산 내역 조회 | — | 준비 중(6절) |

- 회원·업체 등록은 한 번이고, 그 뒤 같은 회원·업체로 인증 신청을 여러 번 보냅니다. 신청 1건이 모두의인증의 인증 접수 1건입니다.
- 신청 상태가 바뀌면 웹훅으로 알려 드리고, 알림을 받으면 조회 API로 최신 내용을 확인하는 방식입니다. 웹훅이 열리기 전까지 신청의 진행 상태는 조회 API(5절)로 확인해 주세요.
- 이 문서에서 **연동사**는 이 API로 모두의인증과 연결하는 곳이고, **연동 서비스**는 API 키가 묶이는 단위(연동사의 서비스 하나)입니다.

## 2. 인증·공통 규칙·호출 한도

### 2-1. 인증 (API 키)

- 모든 요청에 `x-api-key` 머리글로 API 키를 보냅니다. 다른 방식(예: `Authorization: Bearer`)은 받지 않습니다.
- API 키는 모두의인증이 발급해 드립니다(연동사마다 따로 전달). 한 키는 한 연동 서비스에 묶여 있고, 그 연동 서비스가 등록한 것만 조회할 수 있습니다.
- 회원·업체 등록, 등록 확인, 인증 신청, 신청 조회에 같은 키를 씁니다.
- 키가 없거나 잘못됐거나 폐기된 경우에는 보통 `401`입니다. 업체 계정에서 발급한 키는, 그 업체가 승인 상태가 아닌 동안 `401` `OPEN_API_KEY_INVALID`입니다. 이때 키는 폐기되지 않으며, 업체가 다시 승인되면 같은 키가 다시 통합니다. 업체가 삭제되면 그 업체의 키는 모두 폐기되어 다시 쓸 수 없고(`401`), 새 키를 발급받아야 합니다. 업체 키가 아직 활성 상태인 경우에는 업체 승인 상태를 검사하기 전에 분당 한도를 먼저 확인하므로(초과 `429`, 한도 확인 실패 `503`), 업체 미승인 `401`보다 `429`·`503`이 먼저 올 수 있습니다. 폐기된 키는 이 순서와 무관하게 `401`입니다. 키가 없는 요청은 본문(파일)을 읽기 전에 거절하며, 인증 시도 한도를 넘으면 `429`, 한도를 확인할 수 없으면 `503`, 파트너 API가 꺼진 환경에서는 `404`가 먼저 올 수 있습니다.

### 2-2. 공통 규칙

| 항목 | 내용 |
| --- | --- |
| 경로 | 모든 요청은 `/partner/v1/` 아래입니다 |
| 주소 | 시험 환경 주소는 API 키와 함께 안내해 드립니다. 이 문서의 요청 예시는 안내받은 주소를 환경 변수 `MODUCERTI_API_BASE`에, 발급받은 키를 환경 변수 `MODUCERTI_PARTNER_KEY`에 넣어 두었다고 가정합니다(주소 모양 예: `https://partner-api.example.com` — 자리 값) |
| 응답 형식 | JSON(UTF-8). 성공 응답 본문 맨 위에 `"statusCode": 200`이 붙습니다 |
| 응답의 시각 | ISO 8601 UTC 문자열(예: `2026-11-19T03:15:00.000Z`) |
| 시각 입력 형식 | `YYYY-MM-DDTHH:mm:ss` + (선택) 소수초 1~9자리 + **`Z` 또는 `±HH:mm`** (예: `2026-11-19T06:30:00Z`, `2026-11-19T15:30:00+09:00`). 맞지 않으면 그 칸·쿼리의 `FORMAT` 오류입니다. 달력에 없는 날짜·시각과 연도 범위(1900~2200)를 검사하는지는 칸마다 다릅니다(2-4) |
| `data`의 문자열 | 앞뒤 공백(전각·폭 없는 공백 포함)은 지운 뒤 검사합니다. 필수 칸이 공백뿐이면 `REQUIRED`, NUL 문자(`\u0000`)가 있으면 `FORMAT` 오류입니다. 선택 칸은 공백뿐이거나 `null`이면 보내지 않은 것으로 봅니다. 사업자등록번호만은 이 규칙 대신 따로 정리합니다(3-2) |
| 정의되지 않은 칸 | `data` JSON 안에 우리가 정의하지 않은 칸을 보내면 오류 없이 무시합니다 |
| 칸 추가 | v1에서는 응답에 선택 칸이 추가될 수 있습니다. 모르는 칸은 무시하도록 만들어 주세요 |
| 시험용 데이터 | 시험 환경에서는 실제 고객 정보·제품 사진 대신 시험용 이름·이메일·사업자등록번호·주소·사업자등록증·사진·제품명을 써 주세요. 시험 환경의 데이터는 예고 없이 지워질 수 있습니다 |

### 2-3. 호출 한도 (키마다, 기본값)

| 한도 | 기본값 | 넘었을 때 |
| --- | --- | --- |
| 분당 | 60회 | `429` `OPEN_API_RATE_LIMIT_EXCEEDED`, `Retry-After`(초) 머리글이 붙습니다 |
| 하루 | 10,000회 | `429` `OPEN_API_DAILY_QUOTA_EXCEEDED`. 하루는 한국 시간(KST) 0시 기준입니다 |

- 필요한 호출량이 더 크면 알려 주세요. 키별로 조정할 수 있습니다.
- 회원·업체 등록, 등록 확인, 인증 신청, 신청 조회 호출을 합산해 셉니다.
- 요청이 오류(`400` 등)로 끝나도 호출 횟수에 들어갑니다. 키 없는 요청은 인증 시도 한도로 따로 셉니다.
- 키를 보내지 않았거나 잘못된 키로 짧은 시간에 반복 요청하면 `401` 대신 `429` `OPEN_API_AUTH_ATTEMPTS_EXCEEDED`가 나올 수 있습니다(`Retry-After` 있음).

### 2-4. 기능마다 다른 점

위 규칙은 모든 기능에 공통입니다. 아래는 기능마다 다른 부분만 모은 표이고, 자세한 규칙은 각 절에 있습니다.

| 항목 | 회원·업체 등록 (3절) | 인증 신청 (4절) | 신청 조회 (5절) |
| --- | --- | --- | --- |
| 요청 모양 | `multipart/form-data` — `data` + 사업자등록증 파일(선택, 1개) | `multipart/form-data` — `data` + 사진(필수, 1~5장) | GET, 쿼리 |
| 시각 입력 검사 | `agreements.agreedAt` — 형식에 더해 달력에 없는 날짜·시각과 연도(1900~2200)를 **항상** 검사합니다 | 시각 입력 칸이 없습니다 | `updatedSince` — 문자열 형식은 묶음·목록 모두 검사하고, 실제 날짜·시각과 연도 범위(1900~2200)는 **목록에서만** 확인합니다 |
| 같은 요청을 다시 보내면 | 같은 연동 서비스 + 같은 이메일 + 같은 사업자등록번호면 같은 등록입니다. 다른 칸이나 파일이 달라도 바꾸지 않고 처음 `memberId`를 돌려줍니다. `on_hold`는 다시 보내도 처리하지 않고 같은 값을 돌려줍니다. 새로 처리하는 예외(`certificate_required` 등)는 3-5에 있습니다 | 같은 연동 서비스 + 같은 `externalOrderId`면 같은 신청입니다. 같은 내용이면 처음 응답, 다른 내용이면 `409`입니다(4-4) | 읽기 전용입니다 |
| 파일 크기 초과(`413`) | 사업자등록증 파일이 10MB 초과 | 사진 한 장이 10MB 초과 | 해당 없음 |

## 3. 회원·업체 등록

### 회원·업체 등록 — `POST /partner/v1/members`

신청자(회원)와 그 업체를 모두의인증에 **한 번** 등록합니다. 응답의 `memberId`를 저장해 두셨다가 인증 신청(4절)에 실어 주세요.

### 3-1. 요청 모양

`Content-Type: multipart/form-data`로, 부분(part)을 최대 두 개 보냅니다.

| 부분 이름 | 종류 | 필수 | 내용 |
| --- | --- | --- | --- |
| `data` | 글자 | 필수 | 아래 3-2 칸들을 담은 **JSON 문자열** 하나(UTF-8, 64KiB 이하) |
| `businessRegistrationCertificate` | 파일 | 선택(아래) | 사업자등록증 파일 **1개**. PDF·JPG·PNG, **10MB(10,485,760바이트) 이하**. 형식은 파일 이름·`Content-Type`이 아니라 **파일 내용**으로 확인합니다 |

- 이 두 부분 말고 다른 부분은 보내지 마세요(있으면 `400`, 7-3).
- `data`는 **UTF-8 바이트 기준 64KiB(65,536바이트) 이하**입니다(글자 수가 아님 — 한글은 한 글자가 3바이트).
- 사업자등록증을 보내지 않으면 등록은 접수되지만 `certificate_required` 상태로 멈춥니다(3-4).

### 3-2. `data` JSON 칸

| 칸 | 필수 | 규칙 |
| --- | --- | --- |
| `member.name` | 필수 | 신청자 이름. 100자 이하 |
| `member.email` | 필수 | 신청자 이메일. 이메일 형식, 100자 이하. **회원(계정)을 구분하는 기준**입니다(대소문자 구분 없음) |
| `member.phone` | 필수 | 신청자 한국 휴대폰 번호. `01012345678`, `010-1234-5678`, `+821012345678` 모두 받습니다(30자 이하). 연락용이며 회원 구분에는 쓰지 않습니다 |
| `company.businessRegistrationNumber` | 필수 | 사업자등록번호. 하이픈·공백을 지운 뒤 **숫자 10자리**여야 합니다. **업체를 구분하는 기준**입니다 |
| `company.name` | 필수 | 업체명. 255자 이하 |
| `company.representativeName` | 필수 | 대표자명. 100자 이하 |
| `company.postalCode` | 필수 | 우편번호. 5~10자 |
| `company.address` | 필수 | 주소. 500자 이하 |
| `company.detailedAddress` | 선택 | 상세주소. 500자 이하 |
| `agreements.termsVersion` | 필수 | 연동사 화면에서 신청자가 동의한 약관 버전. 50자 이하 |
| `agreements.agreedAt` | 필수 | 동의한 시각. 2-2의 시각 입력 형식 |

`member`, `company`, `agreements`는 각각 통째로 필수인 객체입니다. 빠지면 `400`입니다.

- 길이·필수 검사는 **앞뒤 공백을 지운 뒤** 합니다. 공백뿐인 필수 칸은 `REQUIRED`입니다.
- `agreements.agreedAt`은 형식이 맞아도 달력에 없는 날짜·시각(2월 30일, 25시 등)이거나 연도가 1900~2200 밖이면 `FORMAT`입니다.
- 함께 드리는 OpenAPI 파일은 칸 이름·종류·길이·필수 여부를 담지만, 위 두 규칙과 `data`의 바이트 상한까지는 표현하지 못합니다. 최종 판단은 서버가 합니다.
- `company.businessRegistrationNumber`는 다른 칸과 다르게 정리합니다. 하이픈과 공백(전각 공백 포함)을 자리와 상관없이 지운 뒤 숫자 10자리인지 봅니다. 폭 없는 공백은 지우지 않으므로, 가장자리에 있어도 `FORMAT`으로 거절됩니다.

### 3-3. 응답 (`200`)

```json
{
  "statusCode": 200,
  "memberId": "b3a1c0de-0000-4000-8000-000000000001",
  "status": "registered",
  "registeredAt": "2026-11-19T03:15:00.000Z"
}
```

| 칸 | 뜻 |
| --- | --- |
| `memberId` | 등록 번호(UUID). 저장해 두시고 등록 확인·인증 신청에 실어 주세요 |
| `status` | `registered`, `certificate_required`, `on_hold` 중 하나 (3-4) |
| `registeredAt` | 처음 등록된 시각 |
| `holdReason` | `status`가 `on_hold`일 때만 있습니다. `COMPANY_UNAVAILABLE`(사업자 정보 확인 필요) 또는 `ACCOUNT_UNAVAILABLE`(이메일 계정 확인 필요) |
| `message` | `status`가 `on_hold`일 때만 있습니다. 고객에게 그대로 보여 드릴 수 있는 안내 문구 |

- `statusCode`(정수 `200`)는 모든 성공 응답에 붙는 칸입니다(2-2). OpenAPI 파일에서도 필수 칸입니다.
- `holdReason`·`message`는 `status`가 `on_hold`일 때만 있고, `registered`·`certificate_required`에는 이 두 칸이 없습니다.

`on_hold`일 때의 응답 예:

```json
{
  "statusCode": 200,
  "memberId": "b3a1c0de-0000-4000-8000-000000000003",
  "status": "on_hold",
  "registeredAt": "2026-11-21T03:15:00.000Z",
  "holdReason": "COMPANY_UNAVAILABLE",
  "message": "입력하신 사업자 정보는 모두의인증 확인이 필요합니다. 사업자등록번호를 확인하시거나 고객센터로 문의해 주세요."
}
```

### 3-4. 상태 세 가지

| `status` | 뜻 | 할 일 |
| --- | --- | --- |
| `registered` | 등록이 끝났습니다. 인증 신청 때 이어진 회원·업체를 다시 확인하며, 그 확인을 통과하면 신청을 받습니다(통과하지 못하면 `409`, 4-5) | 없음 |
| `certificate_required` (버전 1.0의 `review_required`) | **사업자등록증 파일이 없어** 등록이 멈춰 있습니다 | 같은 이메일·같은 사업자등록번호로, 이번에는 사업자등록증을 실어 다시 보내 주세요. 같은 `memberId`로 이어서 처리됩니다 |
| `on_hold` ("확인 필요") | **모두의인증 담당자가 확인 중**입니다. 확인이 끝나기 전에는 인증 신청을 받을 수 없습니다(`409` `MEMBER_REVIEW_REQUIRED`) | `message`를 고객에게 보여 주세요. 같은 요청을 다시 보내도 풀리지 않습니다. 문의하실 때는 `memberId`를 알려 주세요(등록 응답에는 `traceId`가 없습니다. 오류 응답을 받았다면 그 응답의 `traceId`도 함께) |

- `on_hold`의 `holdReason`은 두 가지뿐이고, 고정 `message`는 다음과 같습니다.
  - `COMPANY_UNAVAILABLE`: "입력하신 사업자 정보는 모두의인증 확인이 필요합니다. 사업자등록번호를 확인하시거나 고객센터로 문의해 주세요."
  - `ACCOUNT_UNAVAILABLE`: "입력하신 이메일 계정은 모두의인증 확인이 필요합니다. 이메일을 확인하시거나 고객센터로 문의해 주세요."
  - 두 사유가 함께면 `ACCOUNT_UNAVAILABLE`로 알려 드립니다.
- 모두의인증에 이미 있는 회원·업체의 구체적인 상태는 응답에 나오지 않습니다.
- 담당자가 확인을 끝내면 `status`가 `registered`로 바뀌고 `statusChangedAt`(3-7)이 그 시각이 됩니다. **가입 상태 변경 알림(웹훅)은 추후 제공 예정입니다. 그 전에는 등록 확인 조회(`GET /partner/v1/members/{memberId}`)로 확인해 주세요.**
- `certificate_required`가 풀리는 길은 "사업자등록증을 실어 다시 보내기" 하나이고, `on_hold`가 풀리는 길은 담당자 확인 하나입니다.

### 3-5. 같은 등록을 다시 보내면

- **같은 연동 서비스 + 같은 이메일 + 같은 사업자등록번호**면 같은 등록으로 봅니다. 기준은 키 값이 아니라 키가 속한 연동 서비스라서, 키를 바꿔 발급받아도 같은 등록으로 이어집니다. 이메일은 대소문자 구분 없이, 사업자등록번호는 하이픈·공백을 지운 숫자로 비교합니다.
- 같은 등록이면 처음 받은 `memberId`와 지금 `status`를 그대로 돌려주고, 다른 칸이나 파일이 달라도 바꾸지 않습니다. 응답이 끊겨 결과를 모를 때는 그대로 다시 보내셔도 됩니다.
- 다시 보낸 요청도 **3-1·3-2 규칙을 모두 통과해야** 같은 등록으로 확인합니다. 규칙에 맞지 않으면 기존 등록과 상관없이 입력 오류는 `400` `VALIDATION_FAILED`, 사업자등록증 파일 크기 초과는 `413` `FILE_TOO_LARGE`입니다.
- `on_hold`인 등록을 같은 이메일·같은 사업자등록번호로 다시 보내면 처리하지 않고 지금 상태(`on_hold`, 같은 `holdReason`·`message`)를 그대로 돌려줍니다. 파일을 실어도 저장하지 않습니다.
- 예외는 둘입니다. 이 경우 같은 `memberId`에서, 다시 보낸 요청의 내용(필수 칸을 갖춘 `data` + 사업자등록증)으로 처음부터 새로 처리하고, 결과는 `registered`·`certificate_required`·`on_hold` 중 하나입니다.
  1. 처음 등록이 `certificate_required`(파일 없음)였고, 사업자등록증을 실어 다시 보낸 경우.
  2. `registered`인데 그 등록에 이어져 있던 회원 또는 업체가 모두의인증에서 삭제된 경우. 파일 없이 보내면 `certificate_required`로 돌아갑니다. 회원·업체가 삭제된 것이 아니라 비활성이 된 경우에는 다시 처리하지 않습니다.
- 새로 처리하는 요청이라, 연동 서비스가 지금 새 등록을 받을 수 없는 상태면 `403` `PARTNER_UNAVAILABLE`입니다(이미 처리가 끝난 등록을 그대로 다시 보낸 경우는 처음 결과를 돌려줍니다).
- 이메일이나 사업자등록번호가 다르면 다른 등록입니다. 한 사람이 여러 업체를 등록하거나 한 업체에 여러 사람을 등록할 수 있습니다.
- 그래서 `memberId`는 사용자 한 명마다 하나가 아니라 **(회원 이메일, 업체 사업자등록번호) 한 쌍마다 하나**입니다. 한 사람이 업체 두 곳으로 등록하면 `memberId`도 두 개입니다. 연동사 쪽에서는 `memberId`를 이 쌍 단위로 저장해 주세요.

### 3-6. 회원·업체는 이렇게 처리됩니다

- **회원**: 같은 이메일의 모두의인증 회원이 없으면 새로 만듭니다. 있으면 그 회원으로 이어집니다(휴면·잠긴 회원도 이어지고, 인증 신청 때 휴면이거나 활성이면 접수됩니다). 같은 이메일 회원이 둘 이상이거나 비활성·정지 상태이면 `on_hold`(`ACCOUNT_UNAVAILABLE`)입니다. 기존 회원의 정보(이름·연락처 등)는 보내 주신 값으로 바꾸지 않습니다.
- **업체**: 같은 사업자등록번호의 업체가 없으면 보내 주신 정보와 사업자등록증으로 새로 만듭니다. 이 업체에는 직원이 없습니다(신청하신 분도 그 업체의 마스터나 직원이 되지 않습니다. 삭제된 업체는 없는 것으로 봅니다). **연결할 수 있는 승인 업체가 하나로 정해질 때만(사업자등록증을 실어 보낸 경우) 그 업체로 이어지고, 신청만 그 업체로 접수됩니다.** 같은 사업자등록번호의 업체가 여럿이거나 시연 업체만 있는 경우, 또는 회원을 하나로 정하지 못한 경우에는 업체를 이어 붙이지 않고 `on_hold`입니다(아래 조건). 기존 업체의 정보는 바꾸지 않습니다.
- **직원**: 연동 등록으로는 모두의인증 업체 직원 가입이 생기지 않습니다. 기존 업체에 이어질 때도 신청하신 분을 그 업체의 직원으로 가입 요청하지 않고, 업체 마스터에게 알리지도 않습니다. 업체에 소속되는 일은 연동 등록이 아니라 고객이 모두의인증 웹에서 직접 합니다.
  - 고객이 연동으로 낸 신청의 접수를 모두의인증 웹에서 보려면, 고객이 모두의인증 웹에서 그 업체에 소속을 신청해야 합니다. 그 업체의 마스터가 승인하며, 승인할 마스터가 없으면 모두의인증 담당자가 승인합니다.
  - 이미 그 업체의 승인된 직원인 고객은 지금과 같이 그 업체의 자료를 봅니다. 연동 등록이 기존 직원 정보를 바꾸지 않습니다.
  - 소속이 승인되기 전에는 그 회원이 그 업체의 자료를 볼 수 없습니다.
  - 사업자등록증이 없는 등록(`certificate_required`)은 업체를 이어 붙이지 않고, `on_hold`인 등록도 담당자가 풀기 전에는 이어지지 않습니다.
- 업체가 미승인·비활성·시연이거나 같은 사업자등록번호의 업체가 여럿이면 `on_hold`(`COMPANY_UNAVAILABLE`)입니다.
- **늘 접수되는 것은 아닙니다**: 등록이 `registered`여도 인증 신청 때 이어진 회원·업체를 다시 확인하고, 통과하지 못하면 `409` `MEMBER_REVIEW_REQUIRED`(4-5)입니다. 접수가 어느 회원·업체에 속하는지는 등록 응답만으로 판단하지 마세요.
- **연동사가 확인해 주실 것**: 신청자가 그 업체 소속인지와 그 이메일의 주인인지는 **연동사가 확인한 뒤** 보내 주세요. 같은 사업자등록번호의 승인된 업체가 모두의인증에 있으면 신청이 그 업체로 접수되지만, 연동 등록이 그 회원을 그 업체의 직원으로 만들지는 않습니다(위 3-6 직원 항목).

### 3-7. 등록 확인 — `GET /partner/v1/members/{memberId}`

```json
{
  "statusCode": 200,
  "memberId": "b3a1c0de-0000-4000-8000-000000000001",
  "status": "registered",
  "registeredAt": "2026-11-19T03:15:00.000Z",
  "statusChangedAt": "2026-11-19T03:20:00.000Z"
}
```

| 칸 | 뜻 |
| --- | --- |
| `memberId`, `status`, `registeredAt` | 3-3과 같음 |
| `holdReason`, `message` | 3-3과 같음. `status`가 `on_hold`일 때만 있습니다 |
| `statusChangedAt` | 상태가 마지막으로 바뀐(또는 다시 처리된) 시각 |

- `status`와 `on_hold`일 때의 `holdReason`·`message`는 등록 응답(3-3)과 같은 값입니다. 담당자가 확인을 끝내면 `registered`로 바뀌고 `holdReason`·`message` 칸이 사라집니다.
- 등록한 뒤에 이어진 회원이나 업체의 상태가 바뀌어도(삭제·비활성·시연 등) 이 값은 따라 바뀌지 않습니다. 그 경우 `registered`여도 인증 신청 때 다시 확인에서 막히면 `409` `MEMBER_REVIEW_REQUIRED`입니다(4-5).
- 없는 번호이거나 다른 연동 서비스의 번호면 `404` `MEMBER_NOT_FOUND`입니다. 회원·업체 정보는 돌려주지 않습니다.

### 3-8. 요청 예시

```bash
curl -X POST "$MODUCERTI_API_BASE/partner/v1/members" \
  -H "x-api-key: $MODUCERTI_PARTNER_KEY" \
  --form-string 'data={"member":{"name":"신청 담당자","email":"applicant@example.com","phone":"010-0000-0000"},"company":{"businessRegistrationNumber":"000-00-00000","name":"시험 업체","representativeName":"시험 대표자","postalCode":"00000","address":"시험 주소","detailedAddress":"시험 상세주소"},"agreements":{"termsVersion":"2026-11-01","agreedAt":"2026-11-19T06:30:00Z"}}' \
  -F "businessRegistrationCertificate=@./certificate.pdf;type=application/pdf"
```

- `data`는 **`--form-string`** 으로 보내 주세요. curl의 `-F 'data=…'`는 값 안에 `;`가 있으면 그 뒤를 잘라 보냅니다(업체명·주소에 `;`가 들어가면 깨진 JSON이 되어 `400`이 됩니다).
- 위 값은 형식에 맞는 시험용 자리 값입니다. 같은 이메일·사업자등록번호로 다시 보내면 3-5대로 같은 등록이 돌아오니, 새 등록을 시험할 때는 이메일·사업자등록번호를 바꿔 주세요.

등록 확인은 위 등록 응답에서 받은 `memberId`를 경로에 넣어 부릅니다(아래 `<memberId>` 자리).

```bash
curl "$MODUCERTI_API_BASE/partner/v1/members/<memberId>" \
  -H "x-api-key: $MODUCERTI_PARTNER_KEY"
```

## 4. 인증 신청 — `POST /partner/v1/applications`

회원·업체 등록(3절)으로 등록한 회원·업체(`memberId`)의 이름으로 인증 신청 1건을 **사진과 함께** 보냅니다. 응답의 `applicationId`를 저장해 두셨다가 신청 조회(5절)에 써 주세요.

### 4-1. 요청 모양

`Content-Type: multipart/form-data`로 보냅니다. 부분(part)은 글자 부분 하나와 사진 부분 1~5개입니다.

| 부분 이름 | 종류 | 필수 | 내용 |
| --- | --- | --- | --- |
| `data` | 글자 | 필수 | 아래 4-2 칸들을 담은 **JSON 문자열** 하나(UTF-8, 64KiB 이하) |
| `photos` | 파일 | 필수 | 제품 사진 **1~5장**. 같은 이름 `photos`로 장수만큼 반복해 보냅니다. JPG·PNG, **장당 10MB(10,485,760바이트) 이하**. 형식은 파일 이름·`Content-Type`이 아니라 **파일 내용**으로 확인합니다 |

- 이 두 이름 말고 다른 부분은 보내지 마세요(있으면 `400`, 7-3).
- `data`는 **UTF-8 바이트 기준 64KiB(65,536바이트) 이하**입니다(글자 수가 아님 — 한글은 한 글자가 3바이트).
- 사진은 **보낸 순서대로** 저장하고, **첫 번째 사진이 대표 사진**이 됩니다.
- 한 요청의 전체 크기는 최대 약 50MB(사진 5장 × 10MB)입니다. 사진 주소(URL)를 보내는 방식이나 사진만 따로 올리는 경로는 없습니다.
- `Content-Type: application/json` 본문은 받지 않습니다(`400`, 7-3).

### 4-2. `data` JSON 칸

| 칸 | 필수 | 규칙 |
| --- | --- | --- |
| `externalOrderId` | 필수 | 연동사가 정하는 신청 번호. 100자 이하, **쉼표(`,`)는 쓸 수 없습니다**. 같은 신청을 다시 보낼 때의 기준입니다(4-4) |
| `memberId` | 필수 | 회원·업체 등록 응답의 번호. 앞뒤 공백을 지운 뒤 1~100자입니다. 새 신청을 처리할 때 UUID 형식과 같은 연동 서비스의 등록인지 확인합니다 |
| `workspaceId` | 선택 | 연동사 쪽 워크스페이스 구분값. 100자 이하 |
| `product.name` | 필수 | 제품명. 100자 이하 |
| `product.modelName` | 선택 | 모델명. 100자 이하 |
| `product.linkUrl` | 선택 | 제품 링크. `http://` 또는 `https://`로 시작하고 공백이 없는 주소, 500자 이하 |
| `product.note` | 선택 | 담당자에게 전할 메모. 1,000자 이하 |

`product`는 통째로 필수인 객체입니다. 빠지면 `400`입니다.

- 길이·필수 검사는 **앞뒤 공백을 지운 뒤** 합니다. 공백뿐인 필수 칸은 `REQUIRED`입니다.
- 약관 동의 칸은 신청에 없습니다. 회원·업체 등록 때 보내 주신 동의 내용을 그대로 씁니다.
- 제품명·모델명·링크·메모는 모두의인증 담당자가 상담·견적 때 참고하는 정보입니다.
- 함께 드리는 OpenAPI 파일은 칸 이름·종류·길이·필수 여부를 담지만, 공백 처리와 `data`의 바이트 상한까지는 표현하지 못합니다. 최종 판단은 서버가 합니다.

### 4-3. 응답 (`200`)

```json
{
  "statusCode": 200,
  "applicationId": "c4b2d1ef-0000-4000-8000-000000000002",
  "externalOrderId": "ORDER-0001",
  "status": "received",
  "receivedAt": "2026-11-19T03:15:00.300Z"
}
```

| 칸 | 뜻 |
| --- | --- |
| `applicationId` | 모두의인증의 신청 번호(UUID). 저장해 두시고 신청 조회에 써 주세요 |
| `externalOrderId` | 보내 주신 신청 번호 |
| `status` | 접수 응답에서는 항상 `received`입니다. 지금 상태는 신청 조회(5절)로 확인해 주세요 |
| `receivedAt` | 접수된 시각 |

### 4-4. 같은 `externalOrderId`로 다시 보내면

- **같은 연동 서비스 + 같은 `externalOrderId`** 면 같은 신청으로 봅니다. 기준은 키 값이 아니라 키가 속한 연동 서비스라서, 키를 바꿔 발급받아도 같은 신청으로 이어집니다.
- 그래서 `externalOrderId`는 **연동 서비스 전체에서 유일**해야 합니다. 워크스페이스 안에서만 유일한 번호를 쓰면 안 됩니다. `workspaceId`가 달라도 `externalOrderId`가 같으면 같은 신청으로 보고, `workspaceId`도 `data`의 칸이라 값이 다르면 다른 내용(`409`)이 됩니다.
- **같은 내용**이면 처음 받은 응답(같은 `applicationId`·같은 `receivedAt`, `status`는 `received`)을 그대로 돌려주고, 사진을 다시 저장하지 않습니다. 응답이 끊겨 결과를 모를 때는 **같은 내용 그대로** 다시 보내셔도 중복 접수가 생기지 않습니다.
- **다른 내용**이면 `409` `EXTERNAL_ORDER_CONFLICT`이고, 처음 접수한 신청은 바뀌지 않습니다. 내용을 바꾸려면 새 `externalOrderId`로 보내 주세요.
- "같은 내용"은 **`data`의 칸 값(앞뒤 공백을 지운 값)** 과 **사진 파일의 내용·보낸 순서**로 판단합니다. 사진 한 장의 내용이 다르거나, 순서나 장수가 다르면 다른 내용입니다. 사진 파일 이름과 `Content-Type`은 보지 않습니다. `memberId`는 대소문자 구분 없이 비교합니다.
  - 사진을 다시 압축하거나 크기를 바꿔 파일 내용이 달라지면, 바꾼 요청이 입력·사진 규칙을 통과했을 때 `409`가 됩니다. 재전송에는 **처음 보낸 파일 그대로** 써 주세요.
- 재전송도 요청 모양, 사진 규칙, `data`의 필수 칸·종류·길이·문자 규칙을 먼저 검사합니다. 여기서 입력 오류는 `400 VALIDATION_FAILED`, 사진 크기 초과는 `413 FILE_TOO_LARGE`입니다. 검사를 통과하면 기존 신청의 내용을 대조합니다. `memberId`의 UUID 형식과 등록 소유는 새 신청에서만 확인합니다.
- 이미 접수된 신청을 같은 내용으로 다시 보낸 경우는, 그 뒤 사정이 바뀌었더라도(예: 연동 서비스가 새 신청을 받을 수 없는 상태) 처음 응답을 돌려줍니다.

### 4-5. 신청을 접수하지 못하는 경우

입력이 규칙에 맞아도 아래 경우에는 신청을 만들지 않습니다(사진도 저장하지 않습니다).

| 응답 | 언제 | 할 일 |
| --- | --- | --- |
| `400` `VALIDATION_FAILED` (`memberId` / `INVALID`) | 새 신청에서 `memberId`가 UUID 형식이 아니거나, 없는 등록이거나, 다른 연동 서비스의 등록 | 회원·업체 등록 응답의 `memberId`인지 확인해 주세요 |
| `409` `MEMBER_REVIEW_REQUIRED` | 이 `memberId`의 등록으로는 지금 신청을 접수할 수 없어 모두의인증 담당자의 확인이 필요합니다. 등록 상태가 `certificate_required`·`on_hold`인 경우, 그리고 `registered`여도 신청 때 다시 확인에서 이어진 회원·업체를 받을 수 없는 경우(삭제·비활성·미승인·시연 등)입니다 | 아래 설명대로 `GET`으로 등록 `status`를 확인해 주세요. 문의하실 때는 `memberId`와 **이 `409` 응답의 `traceId`**를 함께 보내 주세요 |
| `409` `EXTERNAL_ORDER_CONFLICT` | 같은 `externalOrderId`로 다른 내용이 이미 접수되어 있음(4-4) | 새 `externalOrderId`로 보내거나, 처음 보낸 내용 그대로 다시 보내 주세요 |
| `403` `PARTNER_UNAVAILABLE` | 이 연동 서비스로 지금 새 신청을 받을 수 없음 | 모두의인증에 문의해 주세요 |

- `409` `MEMBER_REVIEW_REQUIRED`는 같은 요청을 자동으로 다시 보내도 풀리지 않습니다. 자동으로 다시 시도하지 마세요.
- 먼저 `GET /partner/v1/members/{memberId}`(3-7)로 등록 `status`를 확인해 주세요.
  - `certificate_required`이면 사업자등록증을 실어 등록을 다시 보낸 뒤 신청해 주세요.
  - `on_hold`이면 `message`를 고객에게 보여 주세요. 담당자 확인이 끝나기 전에는 신청을 받을 수 없습니다.
  - `registered`인데 `409`가 이어지면, 이어졌던 회원·업체가 삭제된 경우에 한해 같은 등록을 사업자등록증과 함께 다시 보내면 새로 처리됩니다(3-5). 비활성이 된 경우는 다시 보내도 처음 값 그대로입니다.
- 그래도 같으면 `memberId`와 이 `409` 응답의 `traceId`를 함께 보내 문의해 주세요.

### 4-6. 요청 예시

```bash
curl -X POST "$MODUCERTI_API_BASE/partner/v1/applications" \
  -H "x-api-key: $MODUCERTI_PARTNER_KEY" \
  --form-string 'data={"externalOrderId":"ORDER-0001","memberId":"<memberId>","workspaceId":"ws-test-01","product":{"name":"시험 제품(무선 충전기)","modelName":"TEST-WC-100","linkUrl":"https://example.com/items/test-0001","note":"시험 신청입니다."}}' \
  -F "photos=@./photo-1.jpg;type=image/jpeg" \
  -F "photos=@./photo-2.png;type=image/png"
```

- `<memberId>`에는 회원·업체 등록 응답에서 받은 번호를 넣어 주세요. 새 신청에는 아직 사용하지 않은 `externalOrderId`를 쓰세요.
- `data`는 **`--form-string`** 으로 보내 주세요. curl의 `-F 'data=…'`는 값 안에 `;`가 있으면 그 뒤를 잘라 보냅니다(메모나 링크에 `;`가 들어가면 깨진 JSON이 되어 `400`이 됩니다).
- 사진은 `-F "photos=@파일"`을 장수만큼 반복합니다. 순서대로 저장되고 첫 장이 대표 사진입니다.
- 같은 `externalOrderId`에 처음과 같은 `data` 값과 사진 파일을 같은 순서로 보내면 처음 접수 응답을 받습니다. 유효한 요청이지만 내용이 다르면 `409 EXTERNAL_ORDER_CONFLICT`입니다(4-4).

## 5. 신청 조회

조회는 읽기 전용이고, 같은 연동 서비스로 보낸 신청만 보입니다. 응답 칸은 세 조회가 같습니다.

조회 범위는 연동 서비스 전체입니다. `workspaceId`로 나눠 보여 주지 않으므로, 워크스페이스별 접근 제어는 연동사가 합니다.

| 칸 | 뜻 |
| --- | --- |
| `applicationId` | 모두의인증의 신청 번호 |
| `externalOrderId` | 연동사가 보낸 신청 번호 |
| `status` | 지금 상태(5-4) |
| `statusChangedAt` | 이 상태가 된 시각. 상태 기록을 바탕으로 계산하며, 기록이 부족하면 그 신청이 마지막으로 수정된 시각(그것도 없으면 접수 시각)을 대신 씁니다. 상태 값은 정확하지만 이 시각은 실제보다 늦을 수 있습니다. 접수 직후에는 `receivedAt`보다 조금 이를 수 있습니다(아래 예시처럼) |
| `receivedAt` | 접수 시각 |

### 5-1. 건별 — `GET /partner/v1/applications/{applicationId}`

```json
{
  "statusCode": 200,
  "applicationId": "c4b2d1ef-0000-4000-8000-000000000002",
  "externalOrderId": "ORDER-0001",
  "status": "received",
  "statusChangedAt": "2026-11-19T03:15:00.100Z",
  "receivedAt": "2026-11-19T03:15:00.300Z"
}
```

- 없는 번호이거나, 다른 연동 서비스의 신청이거나, UUID 형식이 아니면 모두 같은 `404` `APPLICATION_NOT_FOUND`입니다.

### 5-2. 묶음 — `GET /partner/v1/applications?ids=…` 또는 `?externalOrderIds=…`

- `ids`(모두의인증 신청 번호) **또는** `externalOrderIds`(연동사 신청 번호)를 쉼표로 이어 보냅니다. 둘을 함께 보내면 `400` `VALIDATION_FAILED`입니다.
- 한 번에 **최대 50건**(중복을 뺀 개수)입니다. 넘으면 `400` `TOO_MANY_IDS`입니다.
- 쉼표로 나눈 각 항목의 앞뒤 공백은 지웁니다. `ids` 전체는 4,000자, `externalOrderIds` 전체는 6,000자 이하여야 합니다.
- **묶음 조회에는 `after`·`limit`·`state`·`updatedSince`를 생략해 주세요.** 함께 보내면 `after`의 길이·NUL 문자, `limit`의 숫자 형식, `state`의 허용값, `updatedSince`의 문자열 형식을 검사합니다. 위반하면 묶음도 `400 VALIDATION_FAILED`입니다. 이 검사를 통과하면 묶음에서는 네 값을 무시합니다. 실제 달력 날짜와 `after`가 유효한 커서인지는 목록에서만 확인합니다.
- 같은 신청을 `ids`에서 대소문자만 다르게 두 번 보내면 결과에 두 번 담길 수 있으니, 신청 번호는 소문자로 통일해 보내 주세요.

```json
{
  "statusCode": 200,
  "items": [
    {
      "applicationId": "c4b2d1ef-0000-4000-8000-000000000002",
      "externalOrderId": "ORDER-0001",
      "status": "received",
      "statusChangedAt": "2026-11-19T03:15:00.100Z",
      "receivedAt": "2026-11-19T03:15:00.300Z"
    }
  ],
  "notFound": ["00000000-0000-4000-8000-000000000000"]
}
```

- 위는 `ids`로 조회한 예시입니다(`notFound`에 찾지 못한 신청 번호). `externalOrderIds`로 조회하면 `notFound`에는 찾지 못한 연동사 신청 번호가 담깁니다.
- `items`는 요청한 순서입니다(똑같은 값을 반복해 보내면 한 번만 담깁니다).
- 없는 신청, 다른 연동 서비스의 신청, UUID가 아닌 `ids` 항목은 오류 없이 `notFound`에 각 항목의 앞뒤 공백을 지운 값으로 담깁니다. 이유는 구분해 알려 드리지 않습니다.

### 5-3. 전체 재대조 목록 — `GET /partner/v1/applications`

`ids`·`externalOrderIds` 없이 부르면 같은 연동 서비스로 보낸 신청 전체를 쪽 단위로 돌려줍니다. 연동사 쪽 목록과 모두의인증 쪽 목록을 맞춰 볼 때 씁니다.

| 쿼리 | 필수 | 뜻 |
| --- | --- | --- |
| `limit` | 선택 | 한 쪽의 개수. 숫자만, 최대 6자리. 기본 50, 1~200 범위로 맞춰집니다(200 초과는 200) |
| `after` | 선택 | 이전 응답의 `nextAfter` 값을 **그대로** 넣습니다(값의 안쪽 구조는 해석하지 마세요). 빈 문자열은 `after`를 보내지 않은 것과 같습니다. 200자를 넘으면 `400` `VALIDATION_FAILED`(`after` / `MAX_LENGTH`), NUL 문자가 있으면 `400` `VALIDATION_FAILED`(`after` / `FORMAT`), 이 검사를 통과했는데 읽을 수 없는 값이면 `400` `INVALID_CURSOR`입니다 |
| `state` | 선택 | `open`만 가능합니다. 아직 끝나지 않은 신청(`received`, `in_progress`)만 돌려줍니다. 다른 값은 `400` `VALIDATION_FAILED`(`state` / `ONE_OF`) |
| `updatedSince` | 선택 | 2-2의 시각 입력 형식. 그 시각 **이후(같은 시각 포함)에 접수되었거나 상태 기록이 생긴** 신청만 돌려줍니다. 겉으로 보이는 `status`가 같아도 포함될 수 있습니다. 비교는 밀리초 단위이고 그 미만 자리(소수초 넷째 자리부터)는 버립니다. 그래서 보낸 시각보다 1밀리초 미만 이른 기록이 포함될 수 있습니다 |

```json
{
  "statusCode": 200,
  "items": [
    {
      "applicationId": "c4b2d1ef-0000-4000-8000-000000000002",
      "externalOrderId": "ORDER-0001",
      "status": "received",
      "statusChangedAt": "2026-11-19T03:15:00.100Z",
      "receivedAt": "2026-11-19T03:15:00.300Z"
    }
  ],
  "nextAfter": null
}
```

- `nextAfter`는 다음 쪽이 있으면 서버가 만든 문자열이고, 마지막 쪽이면 위처럼 `null`입니다. 다음 쪽을 부를 때는 **서버에서 받은 값을 그대로** `after`에 넣어 주세요(직접 만든 값은 `400 INVALID_CURSOR`입니다).

**쪽 넘기는 방법**

1. 첫 쪽은 `after` 없이 부릅니다(필요하면 `limit`, `state`, `updatedSince` 지정).
2. 응답의 `nextAfter`가 `null`이 아니면, 같은 쿼리에 `after=<nextAfter>`를 넣어 다음 쪽을 부릅니다.
3. `nextAfter`가 `null`이면 끝입니다.

- 정렬은 접수 시각이 이른 것부터이고(같으면 `applicationId` 순), 신청의 상태가 중간에 바뀌어도 순서는 변하지 않습니다.
- **빠지지 않는다는 보장은 `state`·`updatedSince` 없이 읽는 "필터 없는 전체 읽기"에만 해당합니다.** 필터 없이 끝까지 읽으면, 읽는 도중 상태가 바뀐 신청도 빠지지 않습니다. 다만 읽는 도중 새로 접수된 신청은 이번 회차에 안 보일 수 있으니 다음 회차에서 확인해 주세요.
- **필터를 켠 목록은 쪽마다 그 시점의 상태로 다시 거릅니다.** 예를 들어 `state=open`으로 첫 쪽을 받은 뒤 다음 쪽을 받기 전에 다음 쪽 대상 신청이 합격·취소 등으로 바뀌면, 그 신청은 이번 `state=open` 읽기에서 빠집니다. 신청을 빠짐없이 맞춰 보는 용도로는 필터를 쓰지 마세요.
- **권장**: 정확한 전체 대조는 필터 없이 전체 읽기를 하고(하루 1회 정도), 자주 돌리는 가벼운 점검은 건별·묶음 조회(최대 50건)나 `updatedSince`로 합니다. `updatedSince`를 쓸 때는 이전 회차를 시작한 시각보다 여유를 두고 앞당겨 겹쳐 읽어 주세요.
- 쪽을 넘기는 동안 같은 `limit`, `state`, `updatedSince`를 유지해 주세요.
- 신청이 많아질수록 한 번의 전체 읽기에 필요한 쪽 수와 시간이 늘어납니다. 호출 한도를 고려해 주기를 정해 주세요.

### 5-4. 상태 5종

| `status` | 뜻 |
| --- | --- |
| `received` | 신청이 접수된 단계입니다 |
| `in_progress` | 진행 중입니다. 상담, 견적, 시험 준비, 시험 중, **시험이 끝났지만 합격·불합격이 확정되기 전**, **취소를 요청했지만 아직 승인되지 않은** 경우가 모두 여기에 들어갑니다 |
| `passed` | 합격 |
| `failed` | 불합격 |
| `unable` | 취소되었거나 더 이상 진행할 수 없게 처리된 신청 |

- **상태는 되돌아갈 수 있습니다.** 예: 합격과 불합격이 정정되는 경우, 취소 요청이 거절되어 `in_progress`로 돌아오는 경우, 취소가 되돌려지는 경우. `passed`·`failed`·`unable`도 최종값으로 굳히지 말고, 이후 조회에서 값이 바뀔 수 있다고 보고 만들어 주세요.
- 상태 값의 종류(위 5개)는 v1에서 바뀌지 않습니다.
- 모두의인증 쪽의 세부 진행 단계 이름은 전달하지 않고 위 5개로만 보여 드립니다.

### 5-5. 요청 예시

건별 조회는 인증 신청 응답에서 받은 `applicationId`를 경로에 넣어 부릅니다.

```bash
curl "$MODUCERTI_API_BASE/partner/v1/applications/<applicationId>" \
  -H "x-api-key: $MODUCERTI_PARTNER_KEY"
```

묶음 조회(연동사 신청 번호로):

```bash
curl "$MODUCERTI_API_BASE/partner/v1/applications?externalOrderIds=ORDER-0001,ORDER-0002" \
  -H "x-api-key: $MODUCERTI_PARTNER_KEY"
```

전체 재대조 목록(첫 쪽, 그리고 응답의 `nextAfter`로 다음 쪽):

```bash
curl "$MODUCERTI_API_BASE/partner/v1/applications?limit=1" \
  -H "x-api-key: $MODUCERTI_PARTNER_KEY"

curl "$MODUCERTI_API_BASE/partner/v1/applications?limit=1&after=<nextAfter>" \
  -H "x-api-key: $MODUCERTI_PARTNER_KEY"
```

## 7. 오류

### 7-1. 오류 모양

모든 오류는 같은 모양입니다. 응답 머리글 `X-Trace-Id`에도 같은 `traceId`가 붙습니다. 문의하실 때 `traceId`를 알려 주시면 빨리 찾을 수 있습니다.

입력 오류(`400`)의 예:

```json
{
  "statusCode": 400,
  "errorCode": "VALIDATION_FAILED",
  "message": "요청 형식이 올바르지 않습니다.",
  "fieldErrors": [ { "field": "company.businessRegistrationNumber", "code": "FORMAT" } ],
  "traceId": "7f0c2b6e-1d2a-4f61-9a3e-2b9d8c4e5a10"
}
```

그 밖의 오류의 예:

```json
{
  "statusCode": 409,
  "errorCode": "EXTERNAL_ORDER_CONFLICT",
  "message": "같은 신청 번호로 다른 내용이 이미 접수되어 있습니다.",
  "fieldErrors": [],
  "traceId": "7f0c2b6e-1d2a-4f61-9a3e-2b9d8c4e5a10"
}
```

- 분기에는 `errorCode`를 쓰세요. `message`는 한국어 문장이며 바뀔 수 있습니다.
- `fieldErrors`는 입력 오류(`400`)일 때만 채워집니다. `field`는 `member.email`·`product.name`처럼 점으로 잇고, 여러 부분 요청 자체의 문제면 부분 이름(`data`, `businessRegistrationCertificate`, `photos`)입니다. 보내 주신 값은 응답에 담지 않습니다.
- 이 API가 처리하기 전 단계에서 걸러지는 요청은 위 모양이 아닐 수 있습니다(`traceId`·`X-Trace-Id`가 없을 수 있음). 예: 이 문서에 **없는 경로**로 보낸 요청, `Content-Type: application/json`인데 깨진 본문. 이런 응답은 HTTP 상태 코드로만 판단해 주세요. 회원·업체 등록과 등록 확인 두 경로는 `multipart/form-data`(등록)·GET(확인)으로 부르시면 해당 없습니다.
- `fieldErrors[].code`: `REQUIRED`(비었거나 없음), `FORMAT`(형식이 맞지 않음), `MAX_LENGTH`(너무 김), `TYPE`(종류가 다름), `ONE_OF`(허용된 값이 아님), `INVALID`(그 밖의 맞지 않음).

### 7-4. 오류가 겹칠 때 어느 것이 먼저인가 (인증 신청)

아래는 현재 처리 단계입니다. 한 단계에서 여러 조건을 어기면 그중 어떤 오류를 먼저 받을지는 보장하지 않습니다.

1. 본문을 읽기 전에 키·호출 한도와 API 사용 가능 여부를 확인합니다. `401`, `429`, 한도 확인 장애의 `503`, API가 꺼진 환경의 `404`가 이때 나올 수 있습니다.
2. 요청 모양, 사진 장수·크기·형식, `data`의 필수 칸·종류·길이·문자 규칙을 검사합니다. `memberId`도 이때 빈 값·길이·NUL을 검사합니다. 입력 오류는 `400`, 사진 크기 초과는 `413`입니다.
3. 같은 `externalOrderId`의 신청이 이미 있는지 확인 → 있으면 여기서 끝납니다. 같은 내용이면 처음 응답(`200`), 다른 내용이면 `409 EXTERNAL_ORDER_CONFLICT`.
4. 연동 서비스가 새 신청을 받을 수 있는지 → `403 PARTNER_UNAVAILABLE`.
5. 새 신청의 `memberId`가 UUID이고 같은 연동 서비스에 등록된 번호인지 확인합니다. 맞지 않으면 `400`(`memberId` / `INVALID`), 담당자 확인이 필요하면 `409 MEMBER_REVIEW_REQUIRED`입니다.
6. 사진 저장과 접수 → `200`.

- 예를 들어 이미 접수한 번호로 다시 보낼 때 `memberId`가 비면 `400 REQUIRED`, 100자를 넘으면 `400 MAX_LENGTH`입니다(둘 다 `VALIDATION_FAILED`의 칸별 오류). 반면 다른 짧은 문자열을 넣고 2번을 통과하면, UUID 형식을 확인하기 전에 내용 차이로 `409 EXTERNAL_ORDER_CONFLICT`가 나옵니다.
